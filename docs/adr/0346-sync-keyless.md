# ADR 0346: 同期の鍵をアプリが管理し、すべて失われたら自動で始め直す

## 状態

承認済み（2026-11-23）。[ADR 0247](0247-sync-key-approval.md) のうち、回復（最近のログイン・72 時間・画面のボタン）、移行で引き継がないこと、ログアウトで K を捨てること、前の K の画面の言葉を置き換える。0247 の券・commit–reveal の承認・署名つきの作り直し・前の K の印を持たない K へ自動で移らないことは、そのまま使う。

## 状況

同期で各 PC がデータを暗号化するアカウント共通の鍵を、この ADR では K と呼ぶ。2026-10-22 の本番の試験で、試験の PC が本物のアカウントで移行（署名の無い K から署名つきへの作り直し）をした。移行は引き継ぎ（`carry`）を出さず、api は前の K の鍵の行を全部消した。その後の片付けで、新しい K を持つ PC が 2 台とも外され、登録に残る K を持つ PC が 0 台になった。残った PC はサインアウトのたびに K を捨てていたので、どの PC も今の K を持たなくなった（`temporary/sync-key-loss/report.md`）。

今の作りでここから戻るには、人が「同期をリセット」を押し、最近ログインし直して、72 時間待ち、もう一度押す必要があった。画面には「鍵を持つ PC」「鍵を渡す」「新しい鍵を受け取る」が並び、利用者は鍵の仕組みを知らないと次に何をすればよいか分からなかった。

守るものは 2 つで、変えない:

- 運営は中身を読めない（E2E）
- アカウントを乗っ取った人に、利用者の K を渡さない

## 決定

- 画面から「鍵」を消す。同期の状態は、スイッチの行に 4 つの見え方（同期済み · {時刻}・同期しています…・ほかの PC の許可を待っています・準備しています…）で出す。承認の窓は「「{name}」の同期を許可しますか？」と「許可しない／許可する」。「同期をリセット」は容量の上限のときだけ出す。
- 活動中の K を持つ PC（holder）が 0 台になったら、残った PC が手元のファイルから自動で始め直す。いつ始め直してよいかは api がサーバーの時計で決め、`GET /v1/sync/state` の `restart` で返す。口は今の回復（`POST /v1/sync/recovery` と `complete`）を使う。
  - 登録済みで K を持つ PC でも、最後の同期（無ければ鍵の行を置いた時刻）が 7 日より前なら活動中に数えない。始め直しと新しい PC の承認は `state.holders[].active` に従う。
  - 外された holder のどれかが 7 日以内に同期していれば 24 時間待つ。その PC には知らせ、今の K の署名で止められる（今の止める口）。止められたら 7 日は頼み直せない。
  - 7 日より前なら、すぐ始め直す。
  - 最近のログインは求めない。代わりに、頼む PC が、holder が 0 台になる前から登録されていることを求める。0 台になった後に登録した PC は、最近のログイン（5 分）が要る。
- K を作り直すとき（移行・署名つきの作り直し・PC を外した後の作り直し）は、外されていない前の holder の全部へ引き継ぐ。移行も引き継ぐ。外された PC には引き継がない。
- K は uid に結んで保存する。サインアウト（人のログアウト・401 の繰り返し・更新の拒否）では捨てず、別の uid で同期を始めるときだけ捨てる。利用者は、自動の始め直しでの最近のログインの免除と、手動のログアウト後の K の保持を承認した。
- hostId が変わっても今の K を持つ PC は、K から作った署名の鍵で証明して、自分宛ての包みを置いて戻る。外された holder がいて作り直しが済んでいない間（`rotate`）は、証明に最近のログインも要る。
- 自分の行があるのに K を無くした PC は、api に知らせて holder から外れる。秘密を読めなかったときは知らせない。
- 同期の項目があるとき、活動中の holder が 0 台になる登録の解除に使う `DELETE /v1/hosts/{hostId}` は、`confirmLastHolder: true` が無ければ断る（`409 last_holder`）。
- 前の K の印を持たない K（自動の始め直しで作ったもの）へは、前の K を持つ PC は自動で移らない。人が「{name} と同期する」を 1 回押し、承認を通してから移る（0247 のまま。言葉だけ変える）。
- admission は 2 のまま。欄を足すだけにする。新しいアプリは `restart` の欄の有無で新しい api かを見分け、無ければ自分から始め直さない。

細かい形は [plus.md](../plus.md) の「同期の始め直しと登録の外れ（api とアプリの約束）」に記載する。

## 理由

- 鍵の言葉を知らなくても、状態の 4 つで「待てばよい」「どの PC を開けばよい」が分かる。承認の窓は「その PC に同期を許すか」だけを聞けば足りる。
- K が全部失われたとき、サーバーにあるのは手元のファイルの写しである。手元のファイルは消えないので、始め直しで失うのは「ほかの PC がまだ受け取っていない変更」だけになる。人に 72 時間とボタンを強いる意味は小さい。
- 待つ・待たないを外された holder の最後の同期で分けるのは、止められる人がいるかで分けるためである。7 日以内に同期した PC はまだ使われている見込みが高く、24 時間あれば知らせが届く。7 日より前に同期が止まった PC しか無ければ、待っても止める人はいない。
- 最近のログインを外すと、盗んだ refresh token で新しい PC を登録して始め直せてしまう。0 台になる前から登録されていることを求めれば、その PC の鍵（手元の PC の中にある）を持たない限り自動では始め直せない。新しい PC はログインの直後に頼むので、利用者の手間は増えない。
- 始め直した PC が新しい K の holder になっても、前の K を持つ PC は人が押すまで移らず、新しい PC は holder の画面の承認が要る。乗っ取った人が始め直しても、利用者の K は渡らない。
- 移行で引き継がなかったことが、今回の事故のきっかけだった。移行する PC は前の K を持っているので、0247 の印つきの引き継ぎがそのまま使える。
- 外した PC に新しい K を引き継ぐと、外した意味が無くなる。外された PC が新しい hostId で戻るのを証明だけで許すと、盗まれた PC が戻れてしまう。作り直しが済むまでは最近のログインを求めれば、盗んだ PC と refresh token だけでは戻れない。
- 手元のファイルは平文で残るので、サインアウトで K を捨てても守れるものが無い。捨てると、401 の繰り返しのような人の知らないサインアウトで K が失われる。別の uid の K は、混ざると別のアカウントのデータを開いてしまうので捨てる。
- 今回の片付けは api を直接呼んで起きた。最後の holder を外す確かめは、画面ではなく api に置く。
- admission を上げると、古い版のアプリが 426 で止まる。欄を足すだけなら、古いアプリは今のまま動き、新しい api の速い始め直しの恩恵も受ける。

## 影響

- 活動中の holder が 0 台になると、始め直しの待ちが明けた時点で、サーバーの同期データを残った PC の手元のファイルで入れ直す。ほかの PC がまだ受け取っていない変更は、その PC が前の K を持っていれば、「{name} と同期する」の後の取り込みで戻る（同じものは新しい方が残り、もう一方は「同期の写し」に 30 日残る）。
- 乗っ取った人が、乗っ取ったアカウントで最近ログインし、新しい PC を登録すれば、holder が 0 台のときに始め直せる（0247 より短い待ちで）。消えるのはサーバーの写しで、利用者の K と手元のファイルは渡らない。利用者の PC がその後に新しい PC として同期を始めるときは、乗っ取った人の PC の名前で「{name} で Pleiad を開いてください」と出るので、人が気付ける。
- 0 台になった後に登録した PC だけが残る人は、最近のログインの 5 分を過ぎると、「ログインし直す」を 1 回押す。
- 外された PC を登録し直すとき、作り直しが済んでいなければ、ログインし直しが 1 回要る。
- 手元の秘密 `plus:syncAccountKey` に `uid` が増える。サインアウトしても K と同期の手元の状態が残る。
- 状態の `wait` は `kind`（`approval`・`preparing`・`restarted`）の形になり、0247 で足した欄の多くが消える。ops の `syncRecoveryRequest`・`syncRecoveryCancel`・`syncRecoveryComplete` は無くなる（自動になる）。
- api の鍵の行に `lostAt` が、メタに `recoveryStop` が増える。誤りに `409 recovery_stopped`・`409 last_holder` が増える。
- 今止まっている利用者（holder 0 台・外された holder の最後の同期が 7 日より前）は、api とアプリを更新するだけで、すぐ始め直して同期に戻る。
- 新しいアプリと前の版の api の組み合わせでは、自動の始め直しはせず「準備しています…」で待つ。api を先に出す。
