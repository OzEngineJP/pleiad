# 0368 外部 MCP の起動の失敗は次の呼び出しで起こし直し、長い呼び出しを中継で切らない

- 状態: 提案
- 置き換えた: 0238（起動に失敗した後、ターン内では起き直さないこと）

## 状況

Claude の会話で、外部の stdio MCP（`npx -y appium-mcp@1.97.1`）が、最初の呼び出しで `ECONNRESET` になり、その後は同じターンの呼び出しがすべて「MCP 呼び出しに失敗しました」で返った（2026-11-26〜27）。原因は 3 つ重なっていた。

- 中継（`core/context-bridge.mjs` の `handle`）が、依頼の本文を読む前に `req.setTimeout(15000)` を掛けたまま外していなかった。これは接続の無通信の上限なので、ツールの答えを待つ間も効く。15 秒を超える呼び出し（遅延起動を含む最初の呼び出し、Simulator の準備のような長いツール）は、答えを返す前に接続を切られた。
- 起動の待ちの既定は 20 秒だった。保持役から起こした appium-mcp は、冷えた状態の最初の起動で 22.6 秒かかり（同じ機械で 2 回目以降は 2.3〜3.5 秒。2026-11-27 に `connectServer` を一時のデータ置き場で測った）、保持役の記録では、起動のちょうど 20 秒後に止められた例が 11/26〜27 に 33 回あった。
- 0238 の「ターン内では起き直さない」により、一度の起動の失敗で、そのターンの残りの呼び出しがすべて起動を試さずに失敗した。

## 決定

- 中継の 15 秒の無通信の上限は、依頼の本文を読む間だけに掛け、読み終えたら外す。ツールの待ちは、今までどおり `tool_timeout_sec`（既定 60 秒、上限 300 秒）が決める。
- 起動の待ちの既定を 60 秒にする（`startup_timeout_sec` を書いていない登録。上限も今までどおり 60 秒）。
- standby から起こす呼び出しが起動に失敗したら、その呼び出しはエラーで返し、行は「失敗」にする（0238 と同じ）。ツールは一覧の写しのまま広告し続け、**次の呼び出しで新しく起こし直す**。起こし直すたびに、失敗した古い接続は手放す。
- 保持役の MCP の口（`HeldMcpTransport.close`）が呼ぶ `source.stop()` を `holderSource` に戻す（読みの列を終える。段 4a で外れたまま呼ばれ、閉じるたびに例外で後片付けが止まっていた）。

## 理由

- 本文の上限は、本文を送り切らない依頼を残さないためのもので、答えの待ちまで縛る理由は無い。答えの待ちには、すでにツールごとの上限がある。
- 起動に失敗する理由の多くは、一時的な遅さ（冷えた npx、重い作業との競合）で、次に呼べばつながる。起き直さないと、長いターンでは数時間その MCP が使えなくなる。壊れた MCP を呼び続けたときの費用は、呼び出しごとに起動の待ち 1 回分で、エージェントは失敗の返りを見て呼ぶのをやめられる。
- 既定の 20 秒は、測った冷えた起動に足りなかった。60 秒は既存の上限と同じで、設定で短くできる。

## 影響

- 15 秒を超える外部 MCP のツール（起動を含む）が、答えを返せるようになる。
- 起動に失敗した MCP は、行が「失敗」のまま、次の呼び出しで「起動しています」に戻って起き直す。
- 起動しない MCP の呼び出しは、失敗を返すまで最大 60 秒待つ（今までは 20 秒）。
