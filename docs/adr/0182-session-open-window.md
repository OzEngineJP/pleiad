# 0182 会話を開くとき、末尾の窓と提示の枠だけを先に描く

- 状態: 提案（番号は仮。採番し直す）
- 日付: 2026-10-09
- 関連: [ADR 0062](0062-incremental-session-load.md)（差分の読み直し。これを窓の上に載せ替える。置き換えはしない）、[ADR 0179](0179-remote-throughput-and-list-size.md)（大きい返事を `/bulk/<id>` で渡す）、[ADR 0092](0092-seamless-visualization.md)（会話内の可視化）、[ADR 0063](0063-conversation-navigation.md)（会話の移動）

## 状況

会話を開く（`loadSession`）と、履歴の全量と提示（Visualize の HTML・画像の dataUri）の本文が 1 つの返事で届き、画面は全発言を 1 回で描いていた。実データに近い 449 発言・提示 40 件の会話で、返事は 6.5 MB、CPU 4 倍・8 Mbps では中継の往復 100ms で「開く → 触れる」が 9.9 秒、300ms で 16.8 秒、直結でも 4.6 秒かかり、Long Task は最大 2.6〜3.0 秒だった（ほぼスマホで困る）。返事の大半は提示の本文（見えない所にある iframe の中身）で、描画の時間の大半は見えていない行の組み立てだった。

[ADR 0062](0062-incremental-session-load.md) は「開くとき」を全量のまま範囲外にしていた。ここがその続きにあたる。

## 決定

1. **提示の本文は返事に載せず、見えるときに HTTP で取る（B2）**。サーバーは `lazy: true` を付けた `loadSession` で、`content` / `dataUri` が 2048 字以上の提示の本文を `lazy: { i, content?: 長さ, dataUri?: 長さ }` の印に替えて返す（`stubPresent`）。本文は `GET /present-body?sessionId=&i=&at=&field=` で取る（`core/history.mjs` の `findPresentBody`）。成功は `Cache-Control: private, max-age=31536000, immutable`（同じ提示は再訪で取らない）、`nosniff`、CSP `sandbox; default-src 'none'`。見つからないのは 404、`field` が不正・`sessionId` が無いのは 400、dataUri が画像でないのは 415（失敗は `private, no-store`）。画面は印の提示を、本物の iframe と同じ高さ（150px）の枠で置き、`IntersectionObserver`（`#log` の上下 800px）に入ったときに取って差し替える（`web/present-lazy.mjs`・`web/render.mjs`）。枠は押せば手で取れ、取れなかったら押して読み直せる。書き出し・検索・枝・委譲の結果など提示を読む他の経路は、`lazy` を送らないので全量のまま。
2. **末尾の窓だけを読み、手前は上へ送ったときに読み足す（B1）**。`loadSession` に `tail`（発言の数。既定 50）・`tailBytes`（既定 256 KiB。ただし最小 6 件、最大 2000 件）を足す。サーバーは末尾から数と字数の上限に収まる分だけを返し、返事に窓の先頭の絶対位置 `base`・`presentBase`・`total`・`presentTotal` を添える。窓の先頭が AI の発言なら、連続する AI の発言の「続き」の形（見出しを省く `.cont`）が窓の頭で変わらないよう、手前の人の発言まで寄せる（20 件まで）。この寄せにも容量の上限（頼んだ `tailBytes`。無ければ既定の 256 KiB）を付け、次の 1 件を足すと超えるときは寄せず、AI の発言が頭の窓を許す（ツールの結果・入力の大きい AI の発言が続く会話で、さかのぼりだけで返事が上限の数倍にならないように。2026-11-19 追記）。AI が頭の窓では、画面は先頭の行をいったん「続き」として描き、手前を読み足したときに `paintOlder` が境の行を描き直して、実際の手前の発言に合った形に戻す。画面は `state.messages` を「読み込んだ末尾の窓」、`state.base` をその先頭の絶対位置として持ち、DOM の印を絶対位置（`m:<abs>` / `p:<abs>`）にする。上へ送って先頭の 900px 以内に来たら `loadOlder` が `older: true` の `loadSession`（`until`・`presentUntil` までの手前を `tail` 件）で読み足し、`paintBefore` で先頭に足す。読んでいる行の位置は `holdReading` で保つ。読み込み中は会話の先頭に「前の発言を読み込んでいます…」と既存のスケルトンの行（`.older-load`）を出し、失敗したら「前の発言を読み込めませんでした」と「もう一度」、最初まで着いたら「ここが会話の最初です」を出す（`pending.olderLoading` / `olderFailed` / `olderStart`）。脇の検索・目次・`revealMessage` で窓の外へ飛ぶときは、見つかるまで（または全部）手前を読み足してから着く。
3. **ADR 0062 の差分の読み直しは、窓の上でそのまま続ける**。`from` / `presentFrom` は絶対位置で表し、持っている窓の先頭（`base`）から続きだけを読む。差分が合っても、続きが窓に収まらない（`from` が今の履歴の窓の先頭より手前にある）ときは、差分ではなく窓を返す（画面は置き換える。離れている間に大きく育った会話で、窓より大きい続きを一度に送らない。2026-11-19 追記）。窓が足りなくなった（持っている窓より手前が変わった・履歴が短くなった）ときは窓を取り直す。署名の照合は窓の中だけなので、窓の外が書き換わっても気づけない。外は読み足したときに取り直される（書き換わる会話は圧縮・Codex の履歴の書き換えで、いずれも末尾か窓の中に出る）。
4. **開いた直後は末尾の 16 発言を先に描き、手前は手が空いたときに足す（C1）**。16 発言（`FIRST_PAINT_ROWS`）の分だけ描いて 1 コマ返し、残りの窓を `requestIdleCallback`（`timeout: 250`。無ければ 16ms の `setTimeout`）で、1 回あたり 24ms を目安に件数を 2〜48 の間で調整しながら、先頭へ向けて足す（`scheduleBackfill`・`stepBackfill`）。足している間は読んでいる位置を動かさず、実寸の確定（`createHeightSettler`）は足し終わってからまとめて行い、行ごとの i18n と末尾判定の読みも 1 回にまとめる。足している間の上へのスクロール（`maybeLoadOlder`）は待たせ、検索・目次・`loadOlder` は先に足し終えてから進める（`flushBackfill`）。**分けて描かない場合**（全量を 1 回で描く）: 静かな読み直しで末尾にいない、残す行がある（`retained`）、遷移の演出がある、`keepUpTo`・編集中（`chatEdit`）・読み込みの目的の発言（`initialMessageId`）がある。
5. **互換は引数で決める**。サーバーに新しい能力の印は足さない。画面は `lazy` / `tail` / `tailBytes` / `base` 付きの差分 / `older` を送るときだけ新しい形を頼み、サーバーは返事に整数の `base` を付ける。画面は `base` が無い返事を「`base` が 0 で提示は全量」と読む。
   - 古い画面 × 新しいサーバー: 新しい引数を送らないので、`serveFrom`（ADR 0062 の形）か全量のまま。
   - 新しい画面 × 古いサーバー: 新しい引数を知らずに全量を返す。窓つきの差分は古いサーバーで署名が合わず全量に戻る（`joinReply` が null）。遅くなる以外の害はない。
   - `PROTOCOL_VERSION`・`COMMANDS` は変えない。
6. **bulk（ADR 0179）**: 窓の読み込み（`loadAndPaint`・`changeBranch`）と手前の読み足し（`loadOlder`）の返事に `bulk: true` を付ける。サーバーは 64 KiB 以上で、つなぎ先がこの PC でないときだけ `/bulk/<id>` に置く。付けないのは `syncHistory` と窓でない全量の読み込み。この 2 つは返事が「流れの出来事」の後に届き、出来事との順序を守るのが `sessionLoads` だけなので、HTTP に出すと順序が入れ替わりうる。窓の読み込みと読み足しは、返事を待つ間の出来事を `sessionLoads` が抑えている。

## 理由

- 返事の量と描画の量を、会話の長さではなく「窓の大きさ」にする。449 発言の会話で、返事は 6551 KB → 19 KB、描く行は 449 → 57、iframe は 40 → 0 になる。
- 提示の本文を HTTP に出すと、ブラウザーの HTTP キャッシュ（`immutable`）が効き、再訪のコストがほぼ無くなる。窓の外の提示は読み足しまで取らない。
- 位置を絶対位置にすると、窓の先頭がずれても、読み足した行・差分の読み直し・脇の検索・枝の印が同じ番号で話せる。
- 手前を読み足すとき行の高さは仮のままなので、位置を保つのは既存の `holdReading`（基準の行を同じ高さに戻す）に任せ、新しい補正を足さない。
- 能力を引数だけで決めるので、古い画面・古いサーバーのどちらとも壊れない。
- 採らなかった案: ページ番号方式（新しい発言が足されると境がずれる）、サーバーに能力の印を足す（古い側が知らないので結局引数の有無で決める）、提示を別の WS コマンドで取る（HTTP のキャッシュが効かず、WS の順序の後ろに並ぶ）、仮想スクロール（行の高さを知らずに位置を保つのが難しく、会話内の検索・目次・地図・実寸の確定の全部に手が入る）。

## 影響

- **測った値**（449 発言・提示 40 件。CPU 4 倍・8 Mbps。実ブラウザー）: 開く → 触れるまで、直結 4638ms → 946ms、中継 100ms 9934ms → 1399ms、中継 300ms 16801ms → 1063ms。Long Task の最大は 2582ms → 371ms（直結）、3032ms → 334ms（中継 300ms）。上へ送って 7 回の読み足しで先頭に着いても、読んでいる行の位置は 1px 以内で動かない。
- 残る Long Task（350ms ほど）は末尾の 16 発言のレイアウトと実寸の確定の強制レイアウトで、CPU 4 倍の値。これより細かく分けるには、実寸の確定の方式の変更が要る（範囲外）。
- **さかのぼりの容量上限の測った値**（2026-11-19。保存済みの実会話を、画面が受け取る形―ツールの結果は 2,000 字に切った後―で計測）: 11 発言・表示 7.52 MiB の会話（大きい発言が並ぶ）で、上限が無いときは窓が全部（11 件・7,702 KiB、頭は人の発言）に戻ったが、256 KiB の上限では窓は末尾 6 件・5,944 KiB（頭は AI の発言）に留まる。66 発言・表示 0.99 MiB のふつうの会話では、上限の有無で窓は同じ（25 から・41 件・465 KiB）だった。残る問題: 窓の中に選ばれる 1 発言そのものが数 MiB になると（この例ではツールの入力に数 MiB のコマンド実行・画像生成のデータを持つ AI の発言。入力は表示用の切り詰めの対象外）、返事はまだ数 MiB になる。発言 1 件の中身の切り分けはこの決定の範囲外。
- 窓の手前にある提示を指す発言が窓の中にあるとき、提示は読み足すまで、その発言の後ろに単独で出る。同じ名前の `visualize` の参照が窓の境をまたいで複数あると、読み足すまで対が入れ替わりうる。
- 親の会話に戻る分岐の印・圧縮の区切りが窓の手前にあるときは、読み足したときに現れる。目次・脇の検索の件数は読み込んだ分だけだが、目次を開く（`onOpen`）と全部を読み足す。
- 静かな読み直しで窓ごと置き換わる（窓が足りなくなる）と、読み足した分は捨てて窓から取り直す。
- 系譜の読み込み（枝の印）は、窓の手前を会話の概要（`outline`）で埋めて通し番号を揃える（`web/branches.mjs`）。概要は本文を運ばず、指紋と人の発言の抜粋だけ（[ADR 0334](0334-lineage-outline-digest.md)）。
- テスト: `tests/unit/history-window.mjs`・`tests/unit/server-history-window.mjs`（窓・印・読み足し・差分・互換・bulk の配線）、`tests/browser/history-window.cjs`（デスクトップの広い画面で、末尾で開く・読み足しで位置が動かない・提示の本文の遅延・検索から古い発言へ・枝の切り替え）。
- 仕様の今の形は `docs/design.md`「会話を開くときの窓」と `docs/design-system.md`「会話を開く間の見せ方」。
