# 0255 走っているターンを開くとき、もう変わらない頭を発言に畳んで末尾の窓で運ぶ

- 状態: 提案
- 日付: 2026-10-23
- 関連: [ADR 0024](0024-watch-open-session-stream.md)（開いている会話の流れと途中参加のスナップショット）、[ADR 0062](0062-incremental-session-load.md)（差分の読み直し）、[ADR 0182](0182-session-open-window.md)（末尾の窓と手前の読み込み。これを走っているターンにも広げる）、issue #127

## 状況

走っているターンの会話を開くと、`loadSession` の `live` は、ターン前の履歴に加えて、ターンが始まってからの出来事（`stream.events`）を全部返し、画面はそれを最初から 1 件ずつ `onEvent` で再生してから「履歴を読み込み中」を解いていた。出来事には本文・考えた内容の細切れと、ツールの結果の全文が入る（保存済みの履歴は Claude の結果を 2,000 字で切るが、走っている間の `tool.result` は切らない）。サーバーが溜める出来事に上限は無い。

ADR 0182 で保存済みの履歴は末尾の窓だけを運ぶようになったが、走っているターンの分はその外にあった。数時間・数百回のツールを使うターンの途中で開くと、待ちがターンの長さに比例して延びる。fake バックエンドで、ツール 600 回・結果およそ 16 MB のターンの途中に開くと、返事は 17 MB、表示まで 3.3 秒（うち 2.8 秒は 1 回の長い処理）だった。中継越しでは、さらに転送の時間が加わる。

## 決定

1. **出来事を「もう変わらない頭」と「まだ動いている末尾」に分ける**（`web/stream-messages.mjs` の `splitLive`）。分ける位置は、新しい発言が始まる出来事（閉じた発言の後の本文・考えた内容、人の発言・指示・完了通知・人以外の提示）のうち最も後ろのもの。ただし、その手前に結果の無いツール・渡っていない人の発言・吹き出しより先に届いた配達の合図があるなら、それより後ろでは分けない。こうすると、手前の発言はその後の出来事で変わらず、画面の `onEvent` を空の状態から末尾だけで始めても、全部を再生したときと同じ並びになる。分けられる所が無ければ、全部を出来事のまま返す（今までと同じ）。
2. **頭は保存済みの履歴と同じ形の発言に畳み、ターン前の履歴とターンを始めた発言の後ろに並べる**（`core/live-snapshot.mjs`）。畳んだ発言には `live: true` の印を付け、ツールの結果は保存済みの履歴と同じ長さ（`MAX_RESULT_CHARS`）に切って `truncated` を付ける。並べた全体を、保存済みの履歴と同じ `serveHistory` で末尾の窓・差分・提示の印にする。返事の量と描く量は、ターンの長さではなく窓の大きさで決まり、画面は ADR 0182 の仕組み（末尾から先に描き、手前は上へ送ったときに読み足す）をそのまま使う。
3. **末尾だけを `stream.events` で返し、画面は今までどおり再生する**。頭にあった、発言にならない出来事（稼働表示・文脈の量は最後の 1 件、圧縮・中断の知らせ・ターンの結果と終わりは全部）は、末尾の前に流れの順で付ける。末尾の結果は切らない（走っているカードの全文）。
4. **走っている間の手前の読み込み（`older`）も、同じ並びから返す**。窓の先頭が畳んだ発言の中にあっても、通し番号と署名が合う。ターンが終わった後の手前の読み込みは保存済みの履歴から返るので、署名が合わず窓を読み直す（今までの「手前が書き換わった」と同じ扱い）。
5. **ターンが終わったら、畳んだ発言を持つ窓は読み直す**。保存済みの履歴とは発言の区切りが違いうるので、`syncHistory` は添字で照合せず、静かな読み直し（`select(id, { reload: true })`）にする。
6. **畳み方を画面のライブに揃える**。本文の無い（ツールだけの）発言に続く本文の無い `text.end` では区切らない（`onEvent` の `endedWithText`。保存済みの履歴も連続するツールだけの発言を 1 つにする）。`text.end` の uuid を発言に付ける。発言の時刻は手前の出来事の時刻を持ち越す。読むだけの筋（作業の詳細・チャンネル）の畳み方も同じになる。
7. **互換**: 能力の印・`PROTOCOL_VERSION`・コマンドは変えない。古い画面は、届いた発言を履歴として描き、`stream.events` を再生するだけなので、新しいサーバーでもそのまま描ける。新しい画面と古いサーバーは、全部の出来事が届く今までの形のまま。

## 理由

- 遅さの元は「ターンの長さに比例する量を、1 件ずつ描いてから表示する」ことだった。保存済みの履歴にはすでに窓の仕組みがあるので、走っているターンの頭を同じ形にすれば、運ぶ量・描く量・段階的な描き方がすべて流用できる。
- 頭と末尾の境を「新しい発言が始まる所」かつ「未決着のものが無い所」に限ると、画面のライブの状態（開いている発言の入れ物・まとまり・走っているカードの対応）を引き継ぐ仕組みを足さずに済む。未決着のものは末尾に残るので、今までと同じ部品が描く。
- 採らなかった案:
  - 出来事をそのまま新しい順に描く: 細切れの本文はどの発言の続きかが前から追わないと決まらず、逆順では描けない。
  - 画面の側だけで畳む: 描く量は減るが、運ぶ量（結果の全文）が減らず、中継越しのモバイル版の待ちが残る。
  - 走っているカードを、履歴として描いた行に引き継ぐ: 境を自由に置けるが、`state.toolCards`・まとまり・委譲のカードの対応を履歴の行から作り直す仕組みが要り、壊れやすい。未決着のツールが長く走るターン（サブエージェント）でも、その間に親の出来事はほとんど増えないので、末尾に残しても量は小さい。
  - サーバーが溜める出来事に上限を付ける: 途中から参加した画面が手前を描けなくなる。

## 影響

- **測った値**（fake。ツール 600 回・結果およそ 16 MB のターンの途中で開く。手元の Mac の Chrome）: 返事 17 MB → 0.87 MB、表示まで 3.3 秒 → 0.18 秒、Long Task の合計 3,044ms → 150ms。描いた DOM の要素は 46,822 → 24,213（手前は上へ送ったときに読み足す）。
- 走っている間に開いた窓では、続く AI の発言は保存済みの履歴と同じく見出しを繰り返さない（全部を再生していたときは、閉じた発言の後の発言ごとに見出しが出ることがあった）。
- 畳んだ発言のツールの結果は、ターンが終わった後の履歴と同じく 2,000 字で切れる。末尾の走っているカードは全文。
- 走っている間に読み直す画面（作業の詳細は 2.5 秒ごと）は、毎回サーバーで畳む。畳む処理は出来事の数に比例する（ツール 600 回・出来事 3,500 件でおよそ 3ms）。
- テスト: `tests/unit/live-snapshot.mjs`（分け方・頭と末尾をつないだ並びが全部を畳んだものと同じ・結果の長さ・サーバー越しの窓と手前の読み込み・ターンの終わり）。
- 今の形は `docs/design.md`「会話を開くときの窓」。
