# 0165 コンピューターの操作の待ちは、画面の差分で止まるのを待ち、要るときだけ決定モデル（pplx-decider）に 1 回聞く

- 状態: 承認（2026-10-08。利用者が検証の結果を見て判断を任せた）
- 関連: [0072](0072-computer-use-lock-and-stop.md)（ロック・待ち・止める）、[0155](0155-api-keys-in-one-place.md)（API キーの置き場と、選ぶことを外部送信の同意にする）、[0022](0022-delegation-routing.md)（委譲の判定器で決定モデルをすでに使っている）、docs/computer-use.md

## 状況

コンピューターの操作（`ply_computer`）で、エージェントは操作の後に `wait`（決まった秒数）と `screenshot` を繰り返して、画面が落ち着いたか・終わったかを自分で確かめている。この PC の記録（Step 0。Claude Code の会話の記録から集計）では、待ちと確かめが操作の時間の 16〜22%（Studio Pro の 1 回の長い会話を除くと 14.5〜16.4%）で、確かめの 44% は「ダイアログが閉じたか」のような はい/いいえ で答えられる問いだった。1 回の確かめは LLM（Claude）に画面を見せる 1 往復で、数秒かかる。

利用者は、決定モデル（文を生成せず、選択肢ごとの確率を 1 回で返すモデル。Liquid の d1・Typesafe の Jev・Cloudflare の Clef など）でこの確かめを速くできないかを尋ねた（2026-10-08）。先行例を調べると、決定モデルで次の操作を選ぶもの（Jev-Ultrafast・multi-modal-jev-browser など）と、画面の差分で落ち着くのを待つもの（settled-computer・eensh）はあったが、**画面を見せて「終わったか」を決定モデルに聞く待ち**と、決定モデルの UI の画面の正答率の第三者の評価は見つからなかった。

### 検証（2026-10-08、MSI の PC で実施。記録は MSI の `C:\Users\hikar\decision-models-eval\`）

Studio Pro・Chrome・エクスプローラーの 42 場面を録画し（10 fps ほどのコマ・操作の時刻・「終わった」時刻の正解）、秘密の映ったコマを OCR と目視の選別で除いて（36 場面・送ってよいコマだけ）、OpenRouter（d1 だけは Liquid の API 直）へ送った。

**止まった画面の はい/いいえ**（814 問 = 407 組の肯定形・否定形の対。1440×900。正答はしきい値 0.5）:

| モデル | 正答率 | 否定形で答えが正しく逆になる | 往復の中央値 | 1 回の費用 |
|---|---|---|---|---|
| perplexity/pplx-decider-v1.1-27b | **93.9%** | **91.2%** | 898 ms | $0.00003 |
| openai/gpt-6-luna-decisions | 92.9% | 87.7% | 622 ms | $0.00015 |
| Claude Sonnet 5.5（抜き取り 94 問・思考あり） | 81.5% | 67.4% | 2,387 ms | $0.0038 |
| cloudflare/clef | 78.7% | 61.9% | 1,150 ms | $0.00028 |

- 質問を英語にすると d1 は 72.1% → 89.6%（同じ 120 組）に上がった。pplx-decider は日本語 92.5%・英語 93.8% で、言語にほとんど左右されない。
- 720×450 に落とすと、どのモデルも 2〜7 ポイント下がる。

**待ちの再生**（35 場面。A = 固定 3 秒、B = 画面の差分の「変化してから静止」だけ、D = 差分で止まったら決定モデルに「完了したか」を 1 回聞き、いいえなら次の静止で聞き直す）:

| 方式 | 終わる前に進んだ | 時間切れ | 待ちすぎの中央値 | B が正しく待てた 28 場面の合計 |
|---|---|---|---|---|
| A 固定 3 秒 | 5 | 0 | 2.61 s | 84.0 s |
| B 差分だけ | 4 | 3 | 0.50 s | 27.9 s |
| D pplx-decider | **0** | 2（終わらない場面で待ち続けた。正しい） | 1.41 s | 53.6 s |
| D luna | 0 | 3 | 1.15 s | 75.4 s |
| D d1（英語） | 0 | 4 | 1.29 s | 106.7 s |
| D clef | 0 | 5 | 1.79 s | 152.9 s |
| D Claude Haiku | 0 | 8 | 2.52 s | 227.2 s |

- B は速いが、書き出しの進み・エクスプローラーの一覧の読み込み・Chrome の段階的な描画で、途中の静止を「終わった」と取る（4/35）。差分のしきい値をどう選んでも、速さとこの失敗は両立しなかった。
- D は B より 1 回あたり約 1 秒遅いが、終わる前に進む失敗を 0 にし、固定の待ちと Claude に画面を見せて確かめるより速い。

## 決定

- **`ply_computer` に `wait_until` を足す**（`wait` は残す）。引数は `until?: string`（「完了した状態か」の向きの短い はい/いいえ の問い。例: `The export progress dialog is closed`）と `timeout?: number`（秒。上限は `wait` に合わせて決める）。
  - 画面の差分で「変化してから静止」を待つ（差分のしきい値・面積・静止の長さの初期値は検証で選んだ値から始め、実装で詰める）。`until` が無ければ、静止したところで返す。
  - `until` があれば、静止するたびに決定モデルに 1 回聞き、はいの確率が 0.5 以上なら返す。いいえなら次の変化と静止を待って聞き直す。上限に達したら「まだ終わっていない」と最後の確率を返す。
  - 返り値は、待った時間・聞いた回数・最後の確率・終わったか（下の「実装で決めた値」の `wait.status`）。画像は返さない（要ればエージェントが `screenshot` を撮る）。
  - エージェント向けの説明に「`until` は肯定の向き（はい = 完了）で書く。英語が望ましい」と書く（否定の向きは、pplx-decider でも肯定より数ポイント落ちる）。
- **決定モデルは `perplexity/pplx-decider-v1.2` を OpenRouter 経由で使う（2026-11-13 に `pplx-decider-v1.1-27b` から差し替え）。** 画像は長辺 1440 前後に縮めて送る。
  - 差し替えの理由: 2026-11-13 に OpenRouter の `/api/v1/models/perplexity/pplx-decider-v1.1-27b/endpoints` が `endpoints: []`（提供者なし）で、自分のキーでも Pleiad Plus でも v1.1-27b の問いが通らなくなった。v1.2 は提供者 Perplexity があり、`input_modalities` に `image` があり、料金は prompt $0.00000002/token。モデルの説明は v1.2 を「v1.1 27B の後継で API の約束は同じ」としており、応答の読み方（`answers.<名前>.noul`）は変えていない。Pleiad Plus の中継は v1.1-27b と v1.2 の両方を通す。
  - 下の比較表の数字は v1.1-27b を測った 2026-10 の値（v1.2 は測り直していない）。
- **キーは設定 › API キーの OpenRouter のキーを使い、割り当て `computer:decider` を足す**（ADR 0155 の `uses`）。人がキーを選ぶまで画面を送らない。選ぶ欄の下に「`wait_until` に問いを付けたとき、撮った画面が OpenRouter（Perplexity）へ送られます」と書く。選んでいなければ `until` は使えず、差分だけで待ったことを返り値に書く。
- **送らない画面**: 前面の窓が、`ply_computer` が操作できないアプリ（ターミナル・パスワード管理・セキュリティソフト・Pleiad 自身など）のときは聞かず、差分だけで返す。
- **失敗したとき**（OpenRouter の 429・5xx・時間切れ・キーの失効）: 黙って差分だけに落とさず、返り値に「決定モデルに聞けなかった」と理由を書いて返す（エージェントが `screenshot` で確かめ直せるように）。
- 対象はコンピューターの操作だけ。エージェントのブラウザー（agent-browser）は DOM と読み込みの待ちを持つので、今回は使わない。

## 理由

- pplx-decider は、正答率・否定形での一貫性・確率の較正（Brier 0.043）のすべてで最もよく、言語に左右されず、OpenRouter から使えるので API キーを増やさない。1 回 $0.00003 で、待ちの再生 35 場面ぶんでも $0.0013 だった。
- 差分だけ（B）は速いが「途中の静止」で早く進み、その後のクリックが読み込み中の画面に当たる。D はその失敗を防ぐ部品で、遅くなる約 1 秒より、早く進んで操作をやり直す損のほうが大きい。問いを付けるかはエージェントが場面で選ぶ（間違えると困る場面だけ）。
- Claude に画面を見せて確かめる今の形より、正確（93.9% 対 71.6〜81.5%）で、速く（0.9 秒 対 1.9〜2.4 秒）、安い。
- 採らなかった案:
  - d1: 英語なら 89.6% でやや速い（約 0.7 秒）が、日本語では 72% で、否定形をほとんど読まない。画像を送れるのは Liquid の API 直だけで、キーと送り先が 1 つ増える。
  - 公開の d1-3B を手元で動かす（2026-10-08、MSI の RTX 4070 Laptop 8 GB・transformers・bf16。同じ 120 組・英語）: 720×450 なら往復 110 ms と速いが、正答率は 1440×900 でも 720×450 でも 76.7%（API の d1 は 89.6%）。1440×900 の往復は 637 ms で API と変わらない。待ちの再生では「完了」の見落としで時間切れが 11/35 になった。重み 6.2 GB・VRAM 約 6 GB・読み込み約 10 秒で、ライセンス（LFM Open License v1.0）は年間売上 1,000 万ドル以上の法人を商用の許諾の外に置く。公式の速さ（RTX 4090 で画像 17 ms）は 384 px の画像の値。d1-omni-600M は 47〜143 ms だが正答率 60〜68%。GGUF・llama.cpp は試していない。
  - gpt-6-luna-decisions: 正答率は近いが 1 回の費用が 5 倍で、終了の場面で「まだ」と答え続けて時間切れになった。pplx-decider が使えないときの次の候補にする。
  - Clef・Clef-flash: 否定形で答えが逆にならない（55〜62%）。
  - 固定の待ちの秒数を延ばす: 長すぎる場面と足りない場面が同時に残る。

## 実装で決めた値（2026-10-08）

詳しくは docs/computer-use.md「`wait_until` の待ち方」。

- 差分: 長辺 320 の明るさのコマを 100ms ごとに撮る。画素の差 6 を超えた画素が 2.0% 以上で「変わった」、400ms 変わらなければ「静止」。
- 最初から止まっている画面: 1 秒の間に変化が無ければ静止として返す（「いいえ」の後は使わない）。
- `timeout`: 既定 15 秒・上限 30 秒。最後の問いは締め切りを越えて最長 8 秒（往復の上限 6 秒と撮影）。ロックを取り、`computer_batch` には入れない。Antigravity ではロックの待ちを `150 秒 − timeout − 8 秒`（最短 10 秒）で切り、1 回 3 分の上限に収める。
- 結果の `state` は止められたとき以外 `ok`。終わり方は印の行の `wait.status`（`success` / `timeout` / `unverified` / `error`）。
- 動き続ける画面（2026-10-08 の追記）: 問いがあり、キーがあり、前面が送れるアプリなら、静止が来なくても、最後の答えが返ってから（または呼んでから）2 秒（`SETTLE.askEveryMs`）で 1 回聞く。静止を待つだけでは、進捗の表示やアニメーションが止まらない画面で、終わっていても `timeout` まで聞けなかった。2 秒は、往復（数百 ms〜数秒）を足しても 15 秒の既定の待ちで数回聞ける長さで、聞く回数（OpenRouter の課金と 429）を増やしすぎない長さ。数えるのは、その回に画面が変わったときだけ（止まった画面は、いいえ の後に聞き直さない）。
- 返り値の固定の語（2026-10-08 の追記）: 印の行の `wait` は `{ status, screen, answer, reason?, p_yes?, checks, waited_ms }`。前の `done: true` は「決定モデルが はい」と「前面のせいで聞かずに静止で返した」を区別できず、エージェントが確かめていないものを終わったと読んだ。語は会話の言語によらない英語の固定の語にし、Playwright・Selenium の待ちの言い方（`success` / `timeout`）に寄せて、エージェントが言語ごとの文を読み分けずに済むようにする。`success` 以外は、終わったことを確かめていない。
  - 置き場は、新しい行を足さず、既存の印の行（`[ply_computer] {…}`）の `wait` に入れる。画面は印の行を外して文だけを出すので、人には固定の語が見えず、エージェントは 1 行の JSON として読める。文は会話の言語の 1 文にして、「終わった: はい」の行は無くす。

## 影響

- `ply_computer` のツールが 1 つ増え、docs/computer-use.md のツールの表・エージェント向けの指示を直す。
- 設定 › API キーの割り当てに `computer:decider` が増え、ADR 0155 の「使っている所」・削除の確認・差し替えの確かめ直しの対象になる。
- 画面が外部へ送られる経路が 1 つ増える（キーを選んだ人だけ）。

## 追記（2026-11-13）: Pleiad Plus の経路と「未確認」

- `computer:decider` に Pleiad Plus を選べる（[ADR 0155](0155-api-keys-in-one-place.md) の追記）。Plus のときは中継 `POST <PLUS_API>/v1/proxy/openrouter/alpha/decisions` へ ID トークン付きで送る。応答の形（`answers.done.noul`）は OpenRouter と同じ。401 は ID トークンを取り直して 1 回だけ送り直し、`not_plus`・`account_disabled` はアカウントを読み直し、`credit_exhausted` は上限を覚えて次から送らない。
- 送る前に使えないと分かるとき（上限・ログインなし・Plus ではない・メンテナンス）は画面を送らず、差分だけで待って `unverified`（`plus_credit` / `plus_logged_out` / `plus_not_plus` / `plus_maintenance`）で返す。途中で断られたら `error`。印の `wait` に `via: 'plus'`・`reset_at?` を足した。
- 会話の行は、`error` と、`no_key`・`protected_app` 以外の `unverified` に弱い印「未確認」と理由の 1 文を出す。通知は出さない。
