# 0220 バックエンドの契約を、能力の印の明示・エージェントの記述・共通の契約の試験・id の直書きのラチェットで守る

- 状態: 承認（2026-10-18）
- 関連: [0004](0004-multiple-agent-backends.md)（複数のバックエンド）、[0006](0006-normalized-events-protocol.md)（正規化イベント）、[0020](0020-i18n-dictionary-and-ratchet.md)（ラチェットの形）、[0081](0081-control-surface-registry.md)（操作の一覧の載せ忘れの lint）

## 状況

- OpenCode に対応し、その後もエージェントを足していきたい（[issue #91](https://github.com/OzEngineJP/pleiad/issues/91)）。
- バックエンドの抽象（`core/backends/` の 1 エージェント = 1 ファイル、画面は `describeBackends()` の能力の印だけを見る）は大筋で効いていたが、
  `core/backends/` の外に id の直書き（`=== 'claude'`・`['claude', 'codex', 'antigravity']`）が core・画面で 400 件ほどあった。
- 能力の印は、書いていないことが「対応しない」と同じに扱われ、新しいエージェントを足すとエラーにならずに黙って足りなくなる所があった
  （委譲の行き先の一覧・自動の圧縮の設定の行・Pleiad の指示の絞り込み・探索元の数の上限・裏の作業の札の種類）。
- 契約の文書（`docs/multi-backend.md` §2.3）は、server が実際に呼ぶメソッドと受け取るイベントの半分ほどしか書いておらず、
  全バックエンドで同じ契約を確かめる試験も、イベントの形の検査も無かった。

## 決定

- **全部のエージェントに実装させるのではなく、全部のエージェントに「対応する／しない」を書かせる。**
  能力の印の正本を `core/backends/contract.mjs` の `CAPABILITIES`（値の形と、値ごとに要るメソッド）にし、バックエンドは全部のキーに値を書く。
  書いていない・一覧に無い・要るメソッドが無い・メソッドがあるのに印が false、は `npm test` で落とす。
- **抽象はデータと印で行い、基底クラスや共通のターンの実装は作らない。** エージェントごとに違う一覧（CLI の探し方・ロゴ・短い名前・
  自動の圧縮の既定）は、エージェントの記述（`core/backends/agents.mjs`）に 1 つずつ書き、core と画面はそこから作る。
  画面へは `describeBackends()` が `shortLabel`・`brand`・`idleCompaction` を渡す。
- **id で分けていた振る舞いは印にする。** `approvals`（対話の承認を持たない）・`mcpApproval`（MCP のツールの承認を Pleiad が聞く）・
  `instructionsAtStart`（指示は会話の始めにしか効かない）・`failureDiagnostics`（失敗の理由を控えに残す）を足し、承認モードの「確認なし」は
  モードの名前（`full`・`yolo`）ではなくモードの語彙の `autonomy: never` で見る。
- **共通の契約の試験。** エージェントごとの身代わり（LLM を呼ばない）で、全エージェントに同じ契約（1 ターン・履歴の形と uuid・続き・タイトル・
  分岐）を回す（`tests/unit/backend-conformance.mjs`）。能力の印ごとに、その契約を確かめる試験の名前を書かせる（`CAPABILITY_CONTRACTS`）。
- **イベントの形の検査。** バックエンドが出してよいイベントと必ず付けるフィールドを `BACKEND_EVENTS` に書き、試験のサーバーは
  `PLEIAD_BACKEND_CONTRACT=strict` で受け口ごとに照らす。外れたイベントがあれば、どの試験でも `stop()` で落とす。本番では照らさない。
- **id の直書きはラチェットで減らす。** `tests/lint-backends.mjs` が `core/backends/` の外の id とちょうど同じ文字列リテラルをファイルごとに数え、
  基準（`tests/backends-baseline.json`）より増えたら落とし、減ったら基準を下げさせる。そのエージェントだけの事情の行は `backend-allow: 理由` の印で通す。
- **対応表は自動で作る。** 能力の印から `docs/backend-matrix.md` を作り、試験で最新かを見る。

## 理由

- 「全部に実装させる」と、仕組みとして対応できないエージェント（Antigravity の承認など）で詰まる。「決めさせる」なら詰まらず、漏れは防げる。
- 3 つのバックエンドの中身（SDK・JSON-RPC・NDJSON）は違いすぎ、共通のターンの実装にしても得が無い。違いは印とデータで表せば、
  足すエージェントは「記述 + バックエンド + 身代わり」で済む。
- 一度に全部の id の直書きを消すのは大きすぎる（フックだけで 200 件ほど）。ラチェットなら、今日から増えず、減った分は戻らない（ADR 0020・0081 と同じ）。
- イベントの形の検査を試験のサーバー全部に入れると、既存の 470 本ほどの試験がそのまま契約の試験になる。

## 影響

- エージェントを足す手順は `docs/multi-backend.md` §2.9「エージェントを足す」。印を足す手順も同じ節。
- 基準に残っている直書き（フック・MCP とコンテキストの設定の読み方・互換の接続先・委譲の振り分け・Claude のアカウント）は、OpenCode の対応の中で減らす。
- 会話の控えの `antigravityFailures` は、`failureDiagnostics` の印を持つエージェントの失敗の記録の項目として、名前を変えずに使う（保存の形）。
