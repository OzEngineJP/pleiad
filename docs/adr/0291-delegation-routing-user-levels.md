# 0291: 委譲先の自動選択を利用者のレベルと作業の種類で組む。判定のモデルは 1 つ

## 状態

承認（2026-11-06）

- 関連: [0022](0022-delegation-routing.md)（委譲先の自動選択）、[0058](0058-delegation-creative-tier.md)（クリエイティブの段 tv。この ADR で tv を畳む）、[0155](0155-api-keys-in-one-place.md)（API キーの使い道）、[0164](0164-delegation-child-effort.md)（子の思考の強さ）、[0177](0177-judges-via-openrouter.md)（判定を OpenRouter へ）、[0264](0264-delegation-account-scope.md)（アカウントの候補）

## 状況

委譲先の自動選択（0022）は、段（t1〜t4 と創作の tv）・作業の種類（9 種類）・難しさの表がすべてコードの中の決まった形で、利用者は候補の中身と順しか変えられなかった。

- 判定は種類ごとに Jev / Qwen / しないを選べ、「Jev が迷ったら Qwen に聞き直す」があった。実際の自動の委譲の約 87% が Qwen へ切り替わり、切り替わった委譲は委譲先が変わらないことがほとんどで、良くなったという確かめも無い。Qwen は Jev よりずっと高い。
- 難しさを上げる・下げる仕組みを利用者が持てない（「この種類はもっと強いモデルへ」「単発の作業は安いモデルへ」が書けない）。
- クリエイティブの段 tv は `visual` だけのために段の仕組みを複雑にしており、表・思考の強さ・画面・エラーの行のすべてが tv を特別扱いしていた。

## 決定

1. **レベルは利用者のもの。** `delegationRouting.levels` は `{ id, name }` の列（弱い方から強い方。既定は t1〜t4・名前は空で「レベル N」と出す）。名前を付けられる・順を変えられる・足せる（数に上限あり）・消せる（最後の 1 つは消せず、使っている作業の種類があれば移し先を選ぶ）。表（`table`）のセル・`tiers`・`efforts` のキーはレベルの id。
2. **作業の種類も利用者のもの。** `delegationRouting.kinds` は `{ id, name, desc }` の列（既定は今の 9 種類）。`desc` は判定のモデルへ渡す説明（空なら辞書の説明・名前）。`ply_delegate` の `kind` の語彙は設定から組み立て、知らない `kind` は選べる一覧を付けて断る。種類は足せる・名前と説明を変えられる・消せる（最後の 1 つは消せない）。
3. **判定のモデルは 1 つ。** `delegationRouting.judge`（既定は OpenRouter の `perplexity/pplx-decider-v1.2`。`none` は判定しない）。種類ごとの `judgeByKind`・`escalateToQwen`・`escalateToCerebras` は廃止。はいの確率の閾値は 6 つの手がかりすべて 0.5（`DECISION_THRESHOLD`。手がかりごとの閾値は廃止）。**判定が失敗・使えなければ別のモデルは試さず**難しさ `mid` で続ける（`fallback` に理由）。送り先は OpenRouter `/alpha/decisions`（前の版の Jev と同じ口）。
4. **tv は最後のレベルに畳む。** `tiers.tv` の候補は最後のレベルの末尾へ、表の `tv` は最後のレベル、`efforts.tv` の行の既定は捨てる（読むときに直す。`migrateLegacySettings`）。`judgeByKind` は種類ごとに判定器が 1 つでもあれば `judge` を既定のモデル、全部 `none` なら `none` にする。prefs は起動では書き換えず、次に委譲の設定を保存したときに今の形で書く。
5. **使うキーは `judge:routing`。** API キーの使い道は `judge:jev` を `judge:routing` に改める（`judge:cerebras` とあわせて読み替える。明示的に書くと `UNKNOWN_USE`）。Plus の仮想のキー `plus` は `judge:routing` と `voice` に選べる。画面・操作が返すのは `key: { via, hasKey, keyRef, plus }`（前の版の `keys.<サービス>` の形はやめる）。
6. **設定 › 委譲。** 「判定のモデル」の面に判定のモデルの pill（既定・今の値・しない）。「詳しい設定」はレベルを 1 つずつ出し、見出しの pill で切り替え、レベルの操作（名前を変更・上へ・下へ・＋ レベルを追加・削除…）はそのレベルの行の「⋯」へ（削除は赤い字とその場の確認）。候補の行・並べ替え・思考の強さ・「使う / 使わない」のアカウントの行は変えない。作業の種類 × 難しさの表の種類名はボタンで、開くと名前・説明・削除の欄。使用量の方針は「後回しにする使用率」と「週次のペース」の 2 欄（「古いとみなす分」は内部の定数に戻す）。

## 理由

- Qwen への切り替えは、委譲先が変わらない 87% の呼び出しに費用を使っていた。1 つの安い決定モデル（pplx-decider は decisions 口専用で、応答が手がかりの確率だけ）に絞り、外れたときは `mid` で進めるほうが、費用と分かりやすさの両方で良い。
- 難しさの表は人によって向いている強さが違うので、段・種類を利用者の項目にした。コードの中の表を編集させるより、画面で足せるレベルと種類にしたほうが安全で確かめやすい。
- tv を畳むと、表・思考の強さ・エラーの行・画面のすべてが「レベルの列」だけで説明できる。`visual` は t4 を指すだけになる（候補は引き継ぐので挙動は変わらない）。

## 影響

- 前の版の設定（`judgeByKind`・`escalateToQwen`・`tiers.tv`・表の `tv`・`efforts.tv`・`judge:jev`・`judge:cerebras` のキーの割り当て）は読むときに今の形へ直し、次の保存で書き直す。断らない。
- 記録（`routing`）の `judge` はモデルの id（`none` は判定しなかった・使えなかった）。`escalated` は前の版の記録にだけ残る。レベルの記録は `tier`・`tierName`・`tierIndex`（表の順）を持ち、index の無い古い記録は旧「段」の順で読み替える。
- 画面・委譲カード・AI への操作の言葉は「段」から「レベル」に揃える（前の版の記録の表示を含む）。
