# 0330 Claude の transcript を「追記だけのとき」差分で読み、増えた分だけ解析する

## 状態

受容。実機の transcript の複製で、追記後の読み直しが 270 MB で約 1,010 ms → 約 52 ms、485 MB で約 2,110 ms → 約 186 ms に縮んだことを確かめた。保持ヒープは 270 MB のもので全部の行を持つ形の 279 MB → 20 MB、485 MB のもので 529 MB → 124 MB に下がった。

## 状況

`createTranscriptReader`（`core/backends/claude-transcript.mjs`）は、Claude の transcript（`<session>.jsonl`）を読み、`getMessages`・`getCompactions`・履歴の outline・older の読み込み・`loadSession` が共用する。更新のたびにファイル全体を `readFile` で読み、`parseSessionTranscript` で全部の行を `JSON.parse` し直していた。

transcript は育ち続けるログで、数百 MB に届く。実機の 270 MB のもので 1 回の読み込み＋解析に約 1 秒かかり、そのあいだイベントループが止まる。同じ会話に履歴の要求が繰り返し届くたびにこのコストが掛かっていた。同じ読み方をしていた子の transcript（`agent-<id>.jsonl`、`readSubagentEntries`）も同じ問題を持っていた。

差分読みの初版（全部の行を解析器に保持）では、320 MiB のキャッシュ上限を「ファイルの大きさ」で数えていたため、上限を超える transcript（実機に 485 MB の稼働中のものがある）は解析状態を持てず、追記のたびに全件読み直しになっていた。また行をまるごと保持するため 270 MB の transcript で約 279 MB、子 1 件でも数 10 MB のヒープを余計に掴んでいた。

## 決定

### 1. 追記だけの成長を「窓の照合」で見抜く

同じファイルかどうかは mtime や大きさだけで決めない。追記として扱う条件はすべて満たすこと。

- inode（`stat.ino`）とデバイス（`stat.dev`）が前回と同じ（作り直し・置き換えを外す）
- 大きさが増えている
- 先頭 4096 バイトが前回と同じ（先頭から書き換わった別物を外す）
- 前回の解析済み末尾の直前 4096 バイト（追記で食われる途中の行は含めない）が今の同じ位置で一致する

どれか 1 つでも崩れたら、キャッシュごと捨てて全体を読み直す。縮んだ・作り直した・途中を書き換えた・ロールバックや圧縮で中身が変わった版は、すべてこの判定で全体読み直しに落ちる。書き込み途中（読んでいるあいだに変わった）ときは従来どおり結果をキャッシュしない。

### 2. 差分の解釈は状態を持つ解析器が受け持つ

`parseSessionTranscript` を分解し、`createSessionParser`（`core/backends/claude-normalize.mjs`）にした。完結した行は `feed` で逐次与え、最後の未完の行（書き込み途中の行）は `feedTail` で保持する。あとでその行の残りが届いたら `unfeedTail` で取り下げ、行全体を改めて `feed` する。一度解析した行は二度目以降触らない。

- transcript は `\n` 区切りの JSONL なので、追記分を改行で切り、末尾の未完の断片だけを行境界で持ち越す。文字コードの切れ目（マルチバイト）をまたぐ位置では切らず、バイトの区間を丸ごと読んで文字列にしてから処理する
- 追記分の読み取りは `open` + `read` で、前回の末尾の窓（4096 バイト）＋増えた分だけを読む。ファイル全体は読まない
- `systemMarkCollector` の `finish()` は、要約・途中送信の写像・圧縮の印を呼ぶたびに組み立て直す。コレクターは行のうち印の判定に要るフィールド（親子・要約の本文など）だけを持つ

### 3. メッセージの選別（SDK の `getSessionMessages` 相当）は増分にせず、追記のたびに全件でやり直す

解析した行（`entries`）は蓄積されるが、その上で行う親の鎖の選別（`selectMessages`）は、追記後に全部の `entries` に対してやり直す。新しい行が入ると、選ばれる鎖・圧縮（compaction）の境目・途中送信（queued command）のつけ方が、過去の行を含めて変わり得るため、直前の選別結果を部分的に直す安全な方法がない。行の解析（コストの主）だけを増分にし、選別は常に全件でやり直す。

### 4. 解析器は行の「蒸留」形だけを持ち、返す行はバイト位置から読み直す

解析器が全部の行を JSON の形で持つとヒープが transcript なみに育つ。そこで 1 KiB（`SLIM_LINE_BYTES`）を超える行は、SDK の選別が実際に読むフィールドだけに縮めた「蒸留」形（`slimEntry`）で持つ。

- 構造のフィールド（`uuid`・`parentUuid`・`type`・`isSidechain`・`teamName`・`isMeta`・`compactMetadata`・`origin`・`timestamp` など）はそのまま残す
- `message` は role・id・stop_reason・content の骨だけにし、文字列は先頭 1,024 字に縮める。SDK の判定（中断印・`<local-command-…>` などの `startsWith`、ブロックの `type`・`id`・`tool_use_id`・`is_error`）は先頭とこの骨で決まる
- `queued_command` の attachment は SDK が中身（prompt・source_uuid など）を読むので丸ごと残す。ほかの大きいフィールド（`toolUseResult`・`data`・`snapshot`・`summary`・`result` など、選別が読まないもの）は落とす
- 蒸留した `message` ごとにファイル内のバイト位置（`offset`・`len`）を `slimIndex` に残す。SDK が選んで返した行の `message` が蒸留形なら、その位置の行だけを `open` + `read` で読み直して本物の `message` に戻す（`hydrateSlim`）。読み直し中に差し替わっていた版は保持しない
- SDK（`jM`・`ou`・`xC`・`RC` ほか）と下流（`transcriptToMessages`・履歴の組み立て）は入力行を書き換えない（`ou` は `{...row}` の写しを Map に置き換える、`getMessages` は `structuredClone` してから触る）ことをコードと試験で確かめた。守るための複製は入れない

### 5. キャッシュの上限は「保持するメモリ」で数える

- transcript のキャッシュは 4 ファイル・計 320 MiB のままだが、数えるのはファイルの大きさではなく保持量の見積もり（行ごとに `min(バイト長, 8 KiB)`＋読み直して戻した `message` のバイト数）。本文を保持しないので、320 MiB を超える transcript でも見積もりが上限に収まる限り差分読みの記録を保てる（実機の 485 MB で保持は約 124 MB）
- 同じファイルへの並行する要求は 1 本の列にする（`busy`）。複数の要求が同時に解析器の状態を進めると順番が狂うため
- 子の transcript（`readSubagentEntries`）も同じ仕組みで差分読みする。`createSubagentParser` で行を逐次与え、選ばれた鎖の `message` だけ読み直す。子の状態は `sessionId/agentId` ごとに最大 24 件・保持量の見積もりの合計 64 MiB で、超えた分は古い順に捨てる（再要求時に全体を読み直して立て直す）

## 理由

- **追記の見抜きに窓を 2 か所照合する。** 大きさと inode だけでは、「同じ大きさで中身の違う版」「末尾より前が書き換わった版」を見抜けない。先頭の窓は別物へのすり替わりを、末尾の窓は途中の書き換え・巻き戻しを拾う。両方一致しなければ差分読みしない
- **途中の行を持ち越す。** Claude が書き込み途中の行は `\n` で終わっていない。未完の断片を「前の行の続き」として保持し、完結してから一度だけ解析する。未完のまま読み進めても行として確定しないので、二重計上も取りこぼしもない
- **選別を増分にしない。** 追記で過去の行の見え方（圧縮済みか・どの鎖に属するか・途中送信に食われるか）が変わる。正しさを保つには全件でのやり直しが必要で、選別のコストは行の解析に比べ小さい
- **蒸留＋読み直しにする。** SDK が返す履歴は数 10 件なので、返る分だけ行を読み直す方が全行を JSON で持つよりずっと軽い。バイト位置を持つので読み直す行を探す走査も要らない
- **上限を保持量で数える。** ファイルの大きさで数えると、本文の大きい transcript ほど差分読みの恩恵が要るのに記録を持てない。保持するのは蒸留形なので、実際のメモリに見合った数え方ができる
- **子にも同じ仕組みを使う。** 子の transcript も追記だけで育つログで、読む側の構造が同じ。子は最大 24 件持つので、全部の行を Map で持つ形（1 件で数 10 MB）だと合計が際限なく膨らむ。蒸留形にして合計 64 MiB を上限にする

## 影響

- 大きい transcript の 2 回目以降の読み直しが、追記分の読み取り＋解析に縮む。実機の複製で、270 MB: 全体読み約 1,010 ms → 追記後 約 52 ms（152 KiB 追記）、485 MB: 約 2,110 ms → 約 186 ms（63 KiB 追記。SDK の選別が全件分 174 ms を占める）。同じ版の再読はキャッシュから即座に返る（0.2 ms 程度）
- 保持ヒープ（`--expose-gc` で実測、実機の複製）。括弧内は初版（全部の行を保持）との比較: 270 MB の親で 20.4 MB（279.0 MB）、485 MB の親で 123.9 MB（529.0 MB）、60.5 MB の子で 3.0 MB（33.0 MB）。SDK が選んだ履歴だけを持つ従来の形（270 MB で 18.1 MB・485 MB で 49.1 MB）との差は蒸留した行の分で、上限の内側に収まる
- **残る制約 1: 初回の全体読みは変わらず重い。** 270 MB で約 1 秒・485 MB で約 2.2 秒イベントループが止まる（読み取り＋行の解析が大半）。初回読みを止めない対策（分割読み・worker 化）は別の仕事
- **残る制約 2: 窓の外側（中腹）だけを書き換えた細工は見抜けない。** transcript は追記だけで育つ前提で割り切る。見抜けなさそうな変形（縮小・作り直し・先頭や末尾の書き換え）は全体読み直しに落ちる
- 増分読み中・読み直し中にファイルが変わった版は保持しない（従来どおり）。書き込みと読み込みが衝突したときは次の要求で読み直す
- 対象: `core/backends/{claude-normalize,claude-transcript,claude}.mjs`・`tests/unit/claude-transcript.mjs`
