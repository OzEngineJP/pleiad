# 0332 Codex の履歴は差分読みにせず、全ページ読みのままにする

## 状態

提案。実装は入れない。実機の Codex の会話で全ページ読みを測り、いちばん重い会話でも 0.2〜0.4 秒（イベントループの止まりは最大 36 ms）で、差分読みの複雑さに見合わないと判断した。見直す条件は「影響」に書く。

## 状況

Codex の会話は `getMessages`・`getCompactions`・`getSubagentMessages`・巻き戻し・子の一覧のたびに、`core/backends/codex-history.mjs` の `readThread` が `thread/read`（メタデータ）→ `thread/turns/list`（ターンの並び）→ `thread/items/list`（アイテム。最初は 32 件ずつ）を、カーソルが尽きるまで最初のページから読む。`loadSession` は開く・手前を読む・系譜の概要・稼働中の再読のどれでも `history.loadTranscript` を通り、`getMessages` 1 回分の全ページ読みを払う。会話を開いたときの `getCompactions` は、直前の読み（5 秒以内）を使うので 2 度は読まない。

Claude は [ADR 0330](0330-claude-transcript-append-incremental-read.md) で「追記された分だけ読む」差分読みを入れた。Codex にも同じ考えを入れられるかを、先に測って決める。

### 測ったこと

方法: 実機の `~/.codex`（codex-cli 0.160.0）を読み取りだけで使い、`CodexRpc` が起こした `codex app-server` に対して `readThread` を直接呼んだ（保持役は通さない。データ置き場は一時の場所にし、本物の `~/.agent-host` は開かない）。`thread/read`・`thread/turns/list`・`thread/items/list` の往復の回数・時間・応答の大きさと、`threadToMessages`・`codexCompactionsFromHistory` の時間、読みの間のイベントループの遅れ（`monitorEventLoopDelay`、1 ms 刻み）を、同じ会話を 2 回続けて読んで取った。1 回目の方が遅いのは、codex 側の読み出しが冷えているためと見られる。

| 会話（先頭の 8 文字） | ターン | アイテム | `items/list` の往復と応答 | 全ページ読み（1 回目 / 2 回目） | 変換＋圧縮の抽出 | ループの止まり（最大） |

- 1 回の往復は 100〜250 KB・数 ms。時間の大半は往復の待ちで、待っている間はイベントループが空く。サーバーの CPU を塞ぐ処理（変換・圧縮の抽出）は 1 回で 30 ms 以下。
- 会話ごとのアイテム数（`thread_history_1.sqlite` の `thread_items`、2,226 会話）は、中央値 20・90 パーセンタイル 331・99 パーセンタイル 1,392・最大 3,756。1,000 件以上が 45 会話、2,000 件以上が 10 会話。上の表の上位 5 会話は、この 1,000 件以上の 45 会話に入る。大半の会話の全ページ読みは数十 ms で済む（171 件で 26〜45 ms）。
- 実機のサーバーの `slow-commands.log`（2026-11-14）で 1 秒を超えた `loadSession` は 6 件。5 件は Claude（1.98〜2.94 秒）、Codex は 1 件（上の 01a1bdd4 の会話、1,155 ms、同時に走っていた命令 4 件）。同じ会話を単独で読むと 197〜316 ms で、1,155 ms の大半は読み以外の時間になる。同じ時間に `lineage` が 3 件（それぞれ 9〜15 秒）と `listSessions` が走っていたが、内訳の記録は無く、どれが何 ms を食ったかは分からない。
- 1 秒を大きく超える `lineage`（9〜15 秒）の本体（`sessions.lineage`）は `sessions.list()` の結果から家族を引く処理で、履歴の読みを含まない。Codex の履歴の読みとは別の仕事。

### app-server に「前の続きだけ」の読みはあるか

あった（0.160 で実機に確かめた）。

- `thread/items/list` の `cursor` は、文字列（不透明なカーソル）のほかに、`{ "type": "item", "itemId": "<アイテムの id>" }` の位置指定を受ける。この位置の後ろ（`sortDirection: "asc"`）か前（`desc`）だけを返す。`turnId` が必須（無いと `-32602 turnId is required when cursor is an item anchor`）。会話にない `itemId` は `-32602 cursor.itemId does not identify an item in the requested history scope`。アイテムの id は `data[].item.id`。
- 2 ターンの会話（上の 01a17c86）の最後のターン（198 件）で、末尾から 5 件目を位置にして `asc` で読むと、残りの 4 件だけが 1 回 3 ms で返り、全件の読みと id が一致した。末尾から `desc` で `limit: 8` ずつ読み、知っている id に当たるまで読むやり方も、1 回 4 ms で足りた。ターンの一覧（約 4 ms）とメタデータ（約 1 ms）を足しても、条件が揃った再読は 10 ms 前後と見込める（全ページ読みは同じ会話で 292 ms）。
- `thread/turns/list` は既定が新しい順で、不透明なカーソルだけ。ターンの一覧は 1 回 2〜10 ms なので、毎回読んで「どのターンまで知っているか」の照合に使える。
- この位置指定を、このリポジトリが想定する下限の版（codex-cli 0.156 系。ページ読み自体がここから）が受けるかは確かめていない（0.160 の schema にあるのを実機で確かめただけ）。

## 決定

Codex の履歴の読み方は変えない。`readThread` は全ページ読みのままで、差分読みとそのキャッシュは入れない。

測った数字と、差分読みに要る追加の仕組み・危うさとの釣り合いで決めた。決める材料は次のとおり。

## 理由

- **遅さの桁が違う。** Claude は 270〜485 MB の transcript の全読み・全解析で 1〜2 秒、そのあいだイベントループが丸ごと止まった。Codex は最も重い会話でも 0.2〜0.4 秒で、止まりは最大 36 ms。待ちの大半は app-server への往復で、その間は他の命令が進む。会話を開く操作の体感を左右する量ではない。
- **効く会話が少ない。** 全ページ読みが 100 ms を超えるのは 1,000 件以上の会話（2,226 会話のうち 45）に限られる。中央値は 20 件で、読みは数 ms。
- **重い会話は 1〜数個の巨大なターンでできている。** 完了済みのターンを「再利用」する差分では、いちばん重い会話（2 ターン・3,756 件）の大半を占める最後のターンが再利用の外になる。稼働中の会話（差分が最も欲しい場面）では、そのターンが進行中である。
- **進行中のアイテムは書き換わる。** アイテムは `inProgress` から `completed` に同じ id のまま更新される。「前に読んだ最後のアイテムの後ろだけ」では、更新が反映されない。正しく読むには、まだ完了していない最初のアイテムの手前を位置にして、そこから読み直す必要がある（Claude のように「追記だけ」で済む前提が成り立たない）。
- **書き換えを見抜く照合が弱い。** Claude は inode・先頭と末尾の窓で別物と追記を見分けた。Codex の履歴には、同じ強さの印がない。ターンの `status`・`completedAt`・`thread.updatedAt`（秒単位）しか手がかりがなく、会話の圧縮・巻き戻し（`thread/revert`）・編集で完了済みのターンの中身が変わる場合を確実に見抜けるとは言えない。間違えると履歴が古いまま、または欠けたまま画面に出る。これは取り戻しにくい壊れ方で、得られる 0.2〜0.4 秒に見合わない。
- **互換と保持役の制約が増える。** 位置指定のカーソルは新しい版の機能で、下限の版に無ければ読み方が 2 本になる（今も legacy とページ読みの 2 本ある）。1 行 16 MiB の上限での `LINE_OVERFLOW` → 半分に読み直す・画像のページの縮め方・巻き込まれた読みの失敗は、差分でも同じに保たなければならない。キャッシュには件数と保持量の上限・並行する読みの直列化・古い順の破棄（ADR 0330 の仕組み）を、もう一組入れることになる。

## 影響

- Codex の履歴を開く・読み直す動きは変わらない。`core/` のコード・試験は変えていない。測りに使ったスクリプトは一時のもので、リポジトリには入れない（上の「測ったこと」に方法を書いた）。
- **見直す条件.** 次のどれかが起きたら、位置指定のカーソルによる差分読みを改めて検討する。
  - 実機の `slow-commands.log` で、Codex の `loadSession` が単独の読みの遅さで繰り返し 1 秒を超える（今回の 1 件は他の命令の待ちを含む）。
  - 会話の標準的な大きさが上がり、全ページ読みが 1 秒に近づく（今は最大の会話で 0.3〜0.4 秒）。
  - 稼働中の Codex の会話の再読が、短い間隔で何度も繰り返される使い方が出てくる（`loadSession` の呼び出しは画面側に複数あり（`web/client.mjs`・`web/history-pane.mjs`・`web/branches.mjs`）、実際の頻度は今回は数えていない。実機の記録で見えたのは、1 秒を超えた Codex の `loadSession` が 1 日で 1 件だけだったことまで）。
- **入れるときの形.**
  - ターンの一覧（毎回 1〜数 ms）で、並び・`status`・`completedAt` が前回と同じ完了済みのターンの中身は再利用し、最後の 1〜数ターンだけを読み直す。
  - 進行中のターンは、完了していない最初のアイテムの手前を位置にして `asc` で読み直す。
  - ターン id の並びの先頭が一致しない・完了済みのターンの `completedAt` が変わった・位置の id を会話が知らない（`-32602`）・件数が減った、のどれかなら、全ページ読みに落ちる。
  - キャッシュは ADR 0330 と同じ考えで、会話の件数と保持量（画像の `result` は捨てた後の大きさ）の上限を持ち、会話ごとの読みを直列にする。
  - 試験は、差分の結果が全ページ読みの結果と同じになること・書き換えの検出・上限を確かめる。
- **気づいた別の無駄（このADRでは直さない）.** `loadSession` の `older`（手前を読む）で、稼働中のターンがあるときは `liveBody` の内容だけを返し、直前の `history.loadTranscript` の結果を使わない。全バックエンドで読みが 1 回余計に走る。コードを読んだだけで、実機では測っていない。
- 対象: `docs/multi-backend.md`「Codex の履歴の読み出し」に、この判断への参照を足した。
