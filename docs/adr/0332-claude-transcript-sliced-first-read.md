# 0332 Claude の transcript の初回の全部読みを区切り、キャッシュの件数を増やす

## 状態

受容。実機の transcript の複製で、初めて開く記録の全部読み中のイベントループの最大の止まりが、495 MB で 1,702〜2,328 ms → 53〜65 ms、271 MB で 1,369〜1,664 ms → 42〜48 ms に下がったことを確かめた（`perf_hooks.monitorEventLoopDelay`）。合計時間はほぼ変わらない（495 MB: 約 2.7〜3.2 秒 → 約 2.4〜2.7 秒、271 MB: 約 1.7〜2.3 秒 → 約 0.8〜1.0 秒）。

## 状況

ADR 0330 で「追記だけのときは差分で読む」「行は蒸留形で持つ」「上限は保持量で数える」を入れたが、キャッシュに無い記録を初めて開くときの全部読みは同期のままだった。`parseWhole`（`core/backends/claude-transcript.mjs`）が `readFile` のあと全行を `feed` で一気に解釈するので、実機の複製で 495 MB の読み込み＋解釈に約 2.5 秒かかり、そのあいだイベントループが最大 1.7〜2.3 秒止まり、ほかの会話の画面・配信も止まっていた（`~/.agent-host/slow-commands.log` に event-loop 1.7〜2.5 秒の記録）。子の transcript（`readSubagentEntriesNow`、`core/backends/claude.mjs`）の全部読みも同じ構造だった。

また `TRANSCRIPT_CACHE_ENTRIES = 4` は、キャッシュ 1 件が記録の大きさなみのメモリを食っていたころの値で、保持量（蒸留形）で上限を数える今は小さすぎた。件数で先に捨てるため、モーダルで会話や子を次々に開くと、320 MiB の上限に届く前から読み直しが起きていた。

## 決定

### 1. 行の解釈を約 20 ms ごとに区切ってイベントループへ返す

- `feedBufferLines`（`core/backends/claude-transcript.mjs`）を、Buffer 全体を行に切って解釈器へ流す共通の入口にした。`TRANSCRIPT_PARSE_SLICE_MS`（20 ms）を超えるたびに `setImmediate` でいったん返す。親の全部読み（蒸留ありと安全網の蒸留なし）と、子の全部読み（と安全網）の両方がこれを通る。
- `readFile` 自体は libuv の裏で走りイベントループを止めないことを測定で確かめた（495 MB の `readFile` が wall time 240〜490 ms のあいだ、ループの最大の止まりは数十 ms に収まった）ので、読み込み側の分割は入れない。
- 区切りで待っているあいだに追記・差し替えが起きた版は、従来どおり読み終わりの stamp 照合で掴み直す（その版は保持せず、次の要求で読み直す）。同じファイルの読みを直列にする `busy`・同じ版の要求を束ねる `pending` の仕組みは変えない。
- 子の全部読みは、行の解釈のほかに全文の文字列化（`buf.toString`）と別パスの形の検査（`invalidSubagentTranscript`）・版の検出（`transcriptVersion`）もファイルの大きさに比例して止まっていた。版の検出（先頭 20 行の最初の `version`）と形の検査を `createSubagentParser` の `feed` に畳み込み、本文の文字列を作らない形にした。判定は従来の関数と同じで、試験で照合する（末尾の書きかけの行だけは違反に数えない、発言 0 件で `"message"` が残る版は違反、など）。

### 2. SDK の選別は区切らない（SDK の中なので区切れない）

`getSessionMessages` の選別は SDK の内部の同期処理で、こちらからは区切れない。実機の複製での wall time は 495 MB で 240〜810 ms、271 MB で 10〜45 ms（選ばれる鎖の長さや構成で変わる）。ただし区切り導入後の計測で、全部読み全体のイベントループの最大の止まりは 65 ms 以下に収まった。選別が wall time よりずっと短い連続した止まりに分かれている（内部で await を挟む）か、大きい連続した止まりを作っていない。値を記録するだけで、直さない。

### 3. キャッシュの件数を 4 → 16

上限は保持量の見積もり（320 MiB）で数えるので、件数は実効の上限ではなく使い回しの数になる。実機の `~/.claude/projects` 全 1,715 件で「行ごとに min(バイト長, 8 KiB)」の保持量の近似を取った分布: 最大は 495 MB の記録で約 82 MB、見積もり 16 MB を超えるのは 27 件、大半は数 MB 以下。16 件なら小〜中の記録を開き回っても読み直しが起きにくく、大きい記録が混ざるときはバイト上限が先に効くので、件数を増やしても総量は変わらず守られる。

## 理由

- **区切るのは解釈側だけにする。** `readFile` が止めないことは測定で確かめたので、分割読みや worker 化のような重い仕組みは要らない。解釈を 20 ms ごとに区切るだけで、合計時間をほぼ変えずに最大の止まりを数十 ms にできる。
- **区切り中の変更は既存の照合に任せる。** 読み終わりの stamp 照合で「読んだ版と今の版が違う」ことを必ず検出できるので、区切りで返したことによる新しい競合の扱いは要らない。
- **子では別パスの検査を畳み込む。** 全文の文字列化＋全行の再走査は、行の解釈と同じくらいイベントループを止める。解釈器が各行をすでに読んでいるので、版と形の判定をその場で数える方が 2 度読みをやめられて速い。
- **件数はバイト上限の内側で増やす。** 保持量で数える上限のもとでは、件数を増やしても総量は守られる。分布の上では 16 件あれば、上限に届かない範囲で開いた記録を使い回せる。

## 影響

- 初めて開く大きい記録でも、ほかの会話の画面・配信が秒単位で止まらなくなる。止まりの残りは 1 行の大きさと GC に依存する（数 MB の行 1 行の `JSON.parse` は 1 回の区切りを超え得る）。それをなくす worker 化はしない。
- `TRANSCRIPT_CACHE_ENTRIES` が 16 になったことで、同時に読み回せる記録の数が増える。バイト上限（320 MiB の見積もり）より多く持つことはない。
- 子の全部読みは、全文の文字列化と形の検査の分だけ合計時間も短くなる。
- 対象: `core/backends/{claude-transcript,claude-normalize,claude}.mjs`・`tests/unit/claude-transcript.mjs`
