# 0352 使用量の上限で、Pleiad が先回りして止めない

- 状態: 承認（2026-11-25）
- 改めた: [0093](0093-resume-after-usage-limit.md)（上限で止まっている間の指示を送信待ちに置く部分）、[0161](0161-limit-no-auto-resume.md)（「◷ 解除」の時計と、解除時刻まで送信を止める部分）、[0040](0040-delegation-routing-headroom.md)（有効な枠の使用率が 100% 以上なら使えないとする部分）、[0229](0229-opencode-limit-retry-wait.md)（上限で止まった子への `ply_task_send` を解除時刻まで走らせない部分）、[0347](0347-conversation-send.md)（上限で待っている項目の例外）

## 状況

Claude Code は、追加使用量（従量課金）が ON なら、5 時間の枠と週の枠が埋まっても続けて動く。それでも Pleiad は、SDK が流す `rate_limit_event` の `status: rejected` を見ただけで上限と判断し、次のことをしていた。

- 成功したターンを `limited` に書き換え、会話を上限で止めた。
- 解除時刻まで、その会話への送信を送信待ちに置いた（`LIMIT_WAITING`、解除のタイマー、「◷ 解除」の時計）。
- 委譲の振り分けと `server.mjs` の受付で、使用率が 100% の枠を使えないものとして先に断った（`quota_full`、`accountQuotaFull`、`tasks.quotaFull`）。

実際には Claude Code が拒否していないのに、Pleiad だけが先に止まっていた。止まった会話は解除まで人も送れず、追加使用量を許可している利用者の作業が止まった。

## 決定

- 上限と扱うのは、Claude Code が実際に拒否したとき（ターンの失敗）だけにする。`assistant.error: rate_limit`、429 のエラー結果がそれにあたる。`rate_limit_event` の `rejected` だけでは `limit` を出さない。解除時刻・枠は、その前に届いた `rate_limit_event` から、表示のためにだけ取る。
- 成功したターンを `limited` に書き換える処理を消す。
- 上限の間の送信の保留を消す。`LIMIT_WAITING`（送信待ちの `waiting.reason: limit`）、解除のタイマー（`limitReleaseTimers`）、`syncLimitWait`、`recoverLimitWaits`、上限で止まった子の次の回の保留、`limitHeld` が対象。上限で止まったことは `interrupted.reason: limit` と解除時刻として保存・表示するだけにする。人の送信は普通に送り、まだ上限なら、そのターンがまた上限で止まる。
- 委譲の振り分けの `quota_full`（使用率が 100% の枠を使えない）を消す。`server.mjs` の `accountQuotaFull` と `tasks.quotaFull` の事前の断りも消す。使用率が高い枠は「80% 以上は後回し」の降格（`quota_high`、`deferred`）に任せる。5 時間の枠は降格しない。
- 振り分けで使えないとするのは、実際に失敗したスロット（`recently_limited`）と再試行を待っているスロット（`retry_waiting`）だけにする。

## 改めた ADR

- 0093: 「上限で止まっている間の指示は API に渡さず、送信待ちに置く」を改める。上限で止まった会話への指示は、普通に送る。上限の検出と保存（`interrupted.reason: limit`、解除時刻・枠・アカウント）、再開で送るもの、アカウントの自動切り替えをしないことは残す。自動再開の部分は 0132・0161 で既に外れており、本 ADR では戻さない。
- 0161: 次の 3 つを改める。
  - 入力欄の押せない時計「◷ 解除」と、解除前の人の再開を断ること（`LIMIT_WAITING`）。
  - 上限中に送った指示を送信待ちに置き、解除時刻にタイマーで流すこと（起動時とスリープ解除時の置き直しを含む）。
  - 0161 が「解除時刻が分からない上限」だけに適用していた「待たせずにすぐ送る」を、解除時刻が分かる上限にも適用する。
  
  上限で止まった会話は自動で再開しないという決定、上限の検出と保存、会話の末尾の行と「▶ 再開」、送信予定、入力欄のアカウントの札で替えて送る逃げ道は残す。0161 の既知の制限（再起動をまたぐと送信待ちが保留に戻る）は、上限を理由にした送信待ちが無くなるので、上限については当てはまらない。
- 0040: 「有効な枠の使用率が 100% 以上なら使えない」を改める。使用率だけでは使えないと決めず、80% 以上の降格だけを残す。
- 0229: 「上限で止まった子への `ply_task_send` は、解除時刻までは走らせない（`limitHolds` と同じ判断）」を改める。子への送信は、すぐ渡す。
- 0347: 上限で待っている項目が、待っている間に設定を替えたら替えた先で送る例外（`retarget`）を外す。待たせる項目が無くなるため。

## 理由

- Claude Code が続けられるものを、Pleiad が先に止めない。止める判断は、実際に拒否された結果だけにする。
- 解除時刻は予測であって、拒否の事実ではない。追加使用量の ON/OFF は Pleiad から確実には見えないため、予測で止めると外れたときの損が大きい。実際に拒否されたときは、そのターンが止まるので、先回りしなくても安全側に倒れる。
- 保留の仕組み（タイマー・復旧・順番）は、拒否の予測を前提にしていた。前提を外すと、残すだけ複雑さが増える。

## 影響

- 残すもの: `core/slot-limits.mjs` とその引き継ぎ（ADR 0302）、「80% 以上は後回し」の降格、`bots/dispatch` と `routines/runner` の「実際に `limited` になった後だけ休む」、`ops sessions.resume` と上限の再開文（`resume.prompt.limit`）、送信予定。
- 古い記録に `quota_full` の理由が残っていても読めるよう、画面の理由名の表示は残す。
- `docs/design.md`、`docs/agent-delegation.md`、`docs/design-system.md`、`docs/zero-downtime-update/stage2-server-state.md` を今の挙動に更新した。
- 確かめていないこと: 実際の 429 の結果メッセージの形（`subtype: success` かつ `is_error: true` を想定）。実機で拒否されたときの確認が要る。
