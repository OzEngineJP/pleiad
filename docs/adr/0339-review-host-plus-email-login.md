# 0339 iOS の審査員の入り方: 審査用ホストを Plus の審査用アカウントに常にログインさせ、メールとパスワードで入れる

- 状態: 提案（実装済み。本番の設定は別の手順で行う）
- 関連: [ADR 0172](0172-play-review-access.md)（審査専用のホストと審査の招待）・[ADR 0263](0263-accounts-and-hosted-relay.md)（アカウントと公式の中継）・[docs/play-store/review-host.md](../play-store/review-host.md)・[docs/play-store/app-access.md](../play-store/app-access.md)

## 状況

iOS の審査（Guideline 2.1 Information Needed）で、サインインの欄がペアリングのコードで、審査員がサインインできないと差し戻された。Apple は、ユーザー名とパスワードのあるデモアカウントを求める。Play 向けの審査用ホスト（ADR 0172）は、コードを貼ってつなぐ作りで、Plus のログイン（Google・Apple）の先は審査員が入れない。

## 決定

審査員は、Plus に**メールとパスワード**でログインし、公式の中継に並ぶ審査用ホストへ入る。アプリは作り直さない。

1. **ログインの画面**（`account.pleiad.dev/login`、Pleiad Plus 側）に、小さなリンク「メールでログイン」を足す。押すとメールとパスワードの欄が出る。新規登録とパスワード再設定の入口は作らない。Firebase の Email/Password は有効にするが、利用者の自己登録は閉じ、管理者が作った審査用アカウント 1 件だけが使う。
2. **審査用ホストが、審査用アカウントで Plus に常にログインする。** 環境変数 `AGENT_HOST_REVIEW_PLUS_EMAIL` と `AGENT_HOST_REVIEW_PLUS_PASSWORD`（審査モードのときだけ読む）で、Firebase にメールとパスワードでログインする（`core/review-plus-login.mjs`、`core/plus/session.mjs` の `loginWithPassword`）。
   - ログインの保管は `plus-secrets.json`（refresh token だけ。パスワードは置かない）で、起動し直しても続く。更新を拒まれて出されたら、自動で入り直す。失敗は間隔を倍にしながら取り直す。保管が別のメールのものなら捨てて入り直す。
   - 環境変数が無ければ何もしない（今までの招待だけの審査用ホストはそのまま動く）。
3. **その審査用アカウントの端末だけ、承認の窓なしで通す**（`core/remote/plus-link.mjs` の 5a）。条件は、審査モードであること**と**、つないだ端末の uid が、ホスト自身が環境変数でログインして得た uid と同じであること。端末の台数（`devicesPerHost`）と 1 時間の回数の上限は今までどおり効く。普段のホスト（審査モードでない）の承認は変わらない。
4. 審査用の image は `AGENT_HOST_PLUS=1` を持つ（公式の中継の経路を使うため）。

## 理由

- 審査員が欲しいのはユーザー名とパスワードで入れること。ログインの先に審査用ホストが並んでいれば、ペアリングも承認も要らず、1 回のログインで全機能に入れる。
- 自動承認を「審査モード かつ ホスト自身がログインしたアカウントの端末」に絞るので、漏れた先の被害は ADR 0172 の層（価値が無い・足場にさせない・数で抑える・戻せる）の中に収まる。審査用アカウントのパスワードが漏れても、入れるのは操作を絞った審査用ホストだけ。
- 自己登録を閉じ、1 件だけにするので、第三者は登録して入れない。

## 影響

- 審査員が入れ直すたびに端末の鍵が増え、`devicesPerHost` を使い切りうる。管理者が審査用アカウントの上限を上げ、足りなければ古い端末を取り消す。
- `plus-secrets.json` は、コンテナに暗号化の仕組みが無ければ平文。審査用の機械には、ほかの秘密を置かない前提（ADR 0172）。
- 審査用アカウントは、メールの確認済み（`emailVerified`）で、Plus の招待か契約を持つ必要がある。
- 本番の設定（Firebase の Email/Password・審査用アカウント・招待・ログインページと審査用ホストの配備）は、この変更に含まない。
