# bot 削除の移行計画

## 1. 移行対象

bot 削除の導入では、既存の記憶の変更履歴と、削除後も残す会話の扱いが変わる。承認済み（2026-11-06）。この計画は更新時の準備を定めるもので、実データへの適用や公開は含まない。

対象は共通の「あなたについて」、各 bot の記憶、忘れた記憶の復元履歴と変更順の番号、過去の DM・スレッド・ルーティンの会話である。

## 2. 既存データの扱い

更新後の初回起動では、記憶の変更履歴を写しに保存し、移した履歴を読み戻して一致を確認する。共通・他 bot の本文、変更履歴と番号を保持し、移せない履歴があれば起動を止める。未知の内容を空の履歴に置き換えない。

既存の bot と会話は、利用者が削除を確定するまで従来どおり利用できる。削除を確定した場合だけ対象 bot の専用記憶・復元履歴・活動メモ・予約・専用要約を消す。共通記憶と他 bot の記憶は残す。会話本文は閲覧用に残し、ルーティンは一時停止する。

新しい記憶を推測して埋める処理は不要である。履歴が元から無い利用者には空の履歴を用い、会話や記憶の本文から架空の過去の変更を作らない。

## 3. 後方互換

更新済みのデータは旧版で開けない。旧版が変更履歴を空と誤認し、追記や上書きをすることを防ぐため、初回起動で保存形式を更新する。旧版と同じデータを交互に編集する併存期間は設けない。

形式更新の確定前に中断した場合は、元の履歴を残す。その間に旧版で追記された履歴も、更新版の再起動で取り込む。確定後に予期しない旧形式の追記を発見した場合は、その追記を消さず起動を止める。

## 4. 段階的な公開

公開は既存の配布手順に従い、まず退避データのある隔離環境で移行と再起動を確認し、その後に配布対象を広げる。今回の作業では配布しない。

公開を広げる条件は、全件試験の通過、共通・他 bot の履歴保持、移行中断からの再開、旧版の起動拒否、削除した bot の会話から実行できないことの確認である。移行が必要な更新では、互換性検査を回避して無停止で切り替えず、利用者へ更新と再起動を案内する。独自の切り替えスイッチは追加しない。

## 5. 切り戻し（ロールバック）の手順

旧版へ戻すには、更新前に停止した状態で採ったデータ置き場全体の退避が必要である。アプリだけを旧版へ戻したり、形式番号だけを下げたりしてはいけない。

切り戻すときは全アプリを停止し、更新後のデータも別に保管してから、更新前のデータ置き場全体と対応する旧版を復元する。更新後の会話・記憶変更・削除は更新前の退避には含まれない。削除した bot や専用記憶が退避から戻る点も、復元前に利用者へ伝える。

自動で作る移行前の写しは、保存形式の調査と復旧のために残す。bot 定義、会話本文、設定を含む全体の退避の代わりにはならない。削除した記憶が移行前の写しや利用者の退避に残る場合があるため、それらの保管・廃棄も利用者が判断する。

## 6. 既存ユーザーへの影響と告知

bot のサイドバーのメニューと bot ページの「⋯」に削除操作が増える。削除確認には消す情報、残す会話の件数、一時停止するルーティンの件数を示す。削除した bot の会話は一時チャットから閲覧でき、送信・実行・本文の編集はできない。人による会話の題変更・既読・会話単位の削除は維持する。

更新前の案内では、初回起動で保存形式が変わること、旧版への切り戻しには更新前の全体の退避が必要なこと、bot 削除を元に戻せないことを伝える。告知は通常の更新案内に含め、今回の作業からは送信しない。

## 7. 移行の受け入れ条件（AC-M-*）

- AC-M-1: 既存データを更新版で開くと、共通・他 bot の記憶と変更履歴が同じ内容・同じ変更番号で読める。
- AC-M-2: 取り込み失敗や照合不一致では起動が止まり、元の履歴と形式番号が保たれる。原因を除けば次の起動で移行できる。
- AC-M-3: 保存後・形式確定前に停止し、その後旧版で履歴を追記しても、更新版での再開後に追記内容を読める。
- AC-M-4: 形式確定後の片付け中に停止しても再開できる。予期しない旧形式の追記は勝手に消されず、起動停止の理由が示される。
- AC-M-5: 更新済みのデータを旧版で開こうとすると、会話や履歴を書き始める前に拒否される。
- AC-M-6: bot を削除して再起動すると、専用記憶と復元履歴は読めず、共通・他 bot の履歴は読める。過去の会話は読めるが送信・実行できない。
- AC-M-7: 更新前の全体の退避と旧版を復元した隔離環境では、その退避時点の会話・記憶を読める。

## 8. 技術前提（開発者向け）

`DATA_SCHEMA` を 2 から 3 に上げる。SQLite のテーブル構造は変えないため `DB_VERSION` は 2 のまま。旧版は `data-schema.json` の 3 を既存の検査で拒否する。`core/data-schema.mjs` がデータロックを取得し、`schema-migration.mjs` で 2→3 を実施する。形式1は従来の1→2を経由する。

`backup-schema2-<日時>/` へ `VACUUM INTO` による確定済み SQLite の写し、形式番号、元の `memory/log.jsonl` を保存する。履歴を既存 `memory_state` の `memory.log` に移し、同一トランザクション内で読み戻し照合を行う。履歴の `rev` と他の名前空間は変更しない。コミット後に形式番号を3へ原子的に更新し、その後に元ログを外す。番号確定前の再実行では元ログを再び正本として取り込む。

`memory.log.meta` の移行済み印と旧ログのハッシュにより、番号確定後の片付けを再開する。元ログに予期しない追記があれば保全して停止する。新規のデータ置き場は最初から形式3で、履歴がまだ行形式でなければ bot 削除時に行形式へ移す。いずれも旧版を許可しない。

自動退避は削除対象の過去の記憶を含み得る。これは既存の退避保持方針に合わせたもので、削除後の稼働中データからの復元入口には使わない。移行試験は `tests/unit/bot-delete-migration.mjs`、保存形式の既存回帰試験は `schema-migration`・`desktop-updates`・`compat-check`、削除と再起動は `bot-delete`・`bot-delete-guards` で確認する。
